# Person 1 (P1) → Person 2 (P2) Data Interface Contract

**Specification Version**: `contract_v1`  
**Date**: 2026-09-26  
**Provider**: Person 1 (Data & Candidate Generation)  
**Consumer**: Person 2 (Feature Engineering & Modeling)  
**Status**: DRAFT SPECIFICATION (Hand-off executes upon V3 validation)  

---

## 1. Scope and Objective

This contract specifies the formal schema, physical data formats, partitioning, integrity constraints, and cryptographic guarantees governing all datasets and candidate sets transferred from Person 1 to Person 2.

---

## 2. Entity Dataset Contract

### Format & Location
- **Format**: Apache Parquet (`COMPRESSION='ZSTD'`)
- **Partitioning Hierarchy**:
  - `P1/data/entities/train/source1/train_s1_entities.parquet`
  - `P1/data/entities/train/source2/train_s2_entities.parquet`
  - `P1/data/entities/train/source3/train_s3_entities.parquet`
  - `P1/data/entities/test/source1/test_s1_entities.parquet`
  - `P1/data/entities/test/source2/test_s2_entities.parquet`
  - `P1/data/entities/test/source3/test_s3_entities.parquet`

### Schema Guarantee
| Field Name | Type | Constraint | Description |
|---|---|---|---|
| `entity_id` | `VARCHAR` | NOT NULL, PRIMARY KEY | Unique entity identifier (e.g. `S1-123`, `S2-456`) |
| `business_name_raw` | `VARCHAR` | MAY BE EMPTY | Raw source business name |
| `business_address_raw` | `VARCHAR` | MAY BE EMPTY | Raw source business address |
| `country_raw` | `VARCHAR` | MAY BE EMPTY | Raw source country code |
| `business_name_normalized` | `VARCHAR` | MAY BE EMPTY | Standardized business name |
| `business_address_normalized`| `VARCHAR` | MAY BE EMPTY | Standardized business address |
| `country_normalized` | `VARCHAR` | MAY BE EMPTY | Standardized country code |
| `name_clean` | `VARCHAR` | MAY BE EMPTY | Lowercased alphanumeric text |
| `address_clean` | `VARCHAR` | MAY BE EMPTY | Lowercased alphanumeric text |
| `name_tokens` | `VARCHAR[]` | MAY BE EMPTY ARRAY | Tokenized business name array |
| `address_tokens` | `VARCHAR[]` | MAY BE EMPTY ARRAY | Tokenized business address array |
| `name_prefix_1`..`4` | `VARCHAR` | MAY BE EMPTY | Length 1, 2, 3, 4 character prefixes |
| `first_token` | `VARCHAR` | MAY BE EMPTY | Initial whitespace-delimited word |
| `root_token` | `VARCHAR` | MAY BE EMPTY | Common commercial prefix stripped token |
| `house_number` | `VARCHAR` | MAY BE NULL/EMPTY | Canonical house number string (empty when non-extractable) |
| `house_number_norm` | `VARCHAR` | MAY BE NULL/EMPTY | Zero-stripped house number (empty when non-extractable) |
| `postal_code` | `VARCHAR` | MAY BE NULL/EMPTY | 5-to-6 digit postal code (empty when non-extractable) |

### Invariants
1. **Zero Row Loss**: Canonical row count must match raw source row count exactly.
2. **Deterministic Ordering**: All files are sorted by `entity_id ASC` ensuring stable, repeatable row sequencing. (Note: Deterministic row ordering ensures repeatable traversal, but does not constitute proof of bitwise binary reproducibility across different Parquet writer implementations, page sizes, or platform architectures).
3. **Legitimate NULL / Empty Values**: While primary key `entity_id` is strictly non-null, derived fields (such as `house_number`, `postal_code`, `root_token`) legitimately evaluate to empty strings `""` or `NULL` when an entity's address or name does not contain the corresponding feature. P2 consumers must explicitly handle empty/NULL inputs for derived fields.

## 3. Candidate-Pair Contract

### Core Candidate Schema
Candidate files delivered to P2 must adhere to the standard three-column schema:

| Column Name | Type | Description | Example |
|---|---|---|---|
| `source1_entity_id` | `VARCHAR` | Source 1 entity ID | `"S1-100000221"` |
| `candidate_entity_id` | `VARCHAR` | Target entity ID (S2 or S3) | `"S2-456789"` |
| `target_source` | `VARCHAR` | Source partition of target (`'source2'` or `'source3'`) | `"source2"` |

### Training Extension (Labels)
For training candidates only, an authoritative `label` column is appended:
- `label`: `TINYINT` (`1` if pair exists in Ground Truth, `0` otherwise).

### Optional Retrieval Provenance Metadata
If multi-channel provenance is provided, it must be stored in optional trailing columns:
- `channel_bitmask`: `INTEGER` (bitmask indicating which blocking/retrieval channels generated the pair)
- `retrieval_score`: `FLOAT` (retrieval similarity score if generated by dense or sparse retriever)

### Candidate Invariants
1. **Deduplication**: Every `(source1_entity_id, candidate_entity_id)` pair must appear at most once.
2. **Strict Ordering**: Ordered by `source1_entity_id ASC, candidate_entity_id ASC`.
3. **Target Disjointness**: S2 candidates must only reference valid S2 entity IDs; S3 candidates must only reference valid S3 entity IDs.

## 4. Ground Truth Interface

Ground truth remains authoritative and frozen:
- **Location**: `data/train/train_ground_truth.tsv`
- **SHA256**: `70bc1d8a16c667e0155c2105d0ab2ebe41d7e7a85d8a529e3ca81c6c3a5af037`
- **Rule**: P1 candidate generation strictly evaluates against ground truth for recall audit, but never uses GT labels to retrieve candidates.

---

## 5. Verification & Manifest Protocol

Prior to consumption by P2:
1. P1 generates a formal candidate manifest (`candidate_universe_manifest.tsv`) recording:
   - Total pair count
   - Distinct S1 count
   - Distinct target count
   - Recall on Ground Truth
   - Exact file size and SHA256
2. P2 validates SHA256 checksums before loading into feature engineering pipelines.
